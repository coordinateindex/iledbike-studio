# iLedBike Studio architecture

Native local macOS app, built with the installed Xcode compiler and Apple frameworks. No npm, Python runtime packages, web server, account, telemetry or cloud service. Python is used only inside `.venv` for the deterministic cockpit generator.

## Boundaries and data flow

SwiftUI editor → validated `Design` → AppKit rasterizer → bounded RGB pixel array → protocol encoder → explicit command policy → CoreBluetooth transport → indexed device acknowledgements → device-info comparison. The on-screen preview and upload originate from the same raster. PNG/JPEG/GIF imports are downsampled before rendering; GIF import currently uses its first frame.

`PixelDrawingCanvas` edits the same 1296-byte row-major `imagePixels` array used by image import, save/open, PNG export and static-image upload. Pointer positions map to physical cells with the same geometry as the preview. Integer line interpolation fills skipped cells between drag events. Leaving the canvas breaks the interpolation path; one gesture remains one undo entry. The editor retains at most 100 complete image snapshots, with redo cleared after a new edit. History is session-only and is reset when another design is opened. No new BLE commands or saved-file schema were added.

Native `ColorPicker` controls expose the macOS color wheel and sliders for message and brush colors. Selection is converted into opaque sRGB hex values; the existing encoder maps each channel to four bits. This exposes the 4096 combinations the upload format can represent without claiming perceptual color accuracy on the hardware.

The app discovers the advertised 36×12 iLedBike profile. The operator selects a discovered peripheral. No writes occur just from editing or opening a design. Connection enables notifications and sends a device-info query. Sending replaces the ordinary display program. An explicit checkbox additionally replaces double-flash state 5 (`0x1A`) with the same design. It defaults on and persists through SwiftUI `AppStorage` under `replaceFlashingMode`. This app-wide preference survives reconnects and restarts, applies to the selected panel, and is separate from design files. Changing it never sends content automatically. Artwork writes to every other driving state remain blocked, as do remote settings, pairing, resets, authentication/password changes and firmware upload (`0xFE/0xFF`). Existing panel content cannot currently be read back; Save design preserves designs made by this app, not a factory backup.

## Distinctions and scales

- Preserve the semantic distinction between ordinary content, unwanted hazard artwork, the four directional/brake slots, remote configuration and firmware all the way from UI intent to the final BLE write. Only ordinary content and explicitly selected state 5 have artwork writers; display power and active-mode selection are separate operations described below. State 5 is a fixed enum target, not an arbitrary slot number. The write boundary rejects all other driving slots even during an authorized flash replacement.
- Passive notifications distinguish the active mode but do not identify the physical button that caused it. Correlating labeled user actions mapped modes 1–4 to forward/left/right/brake and 5 to double-flash. Replacing state 5 changes every route to that artwork, including hazard/emergency use; it cannot selectively remove a center-button transition. Duplicating the design changes visible output without changing firmware routing.
- The ordinary and flash uploads are sequential, not atomic. Each announcement uses its own opcode and acknowledgement, then the existing indexed chunk transport. One final settings comparison covers both. A timeout may leave only the ordinary display updated; disconnect clears pending stages and no automatic retry occurs.
- Pixel fidelity is bounded by 36×12 physical LEDs and the panel's nonlinear RGB444 color encoding. Large source files do not imply greater output capability. Text rasterization and image fitting occur before upload; preview shows the quantized colors.
- An application chunk and a BLE write are different units. Application data uses up to 1024 bytes with an index and XOR checksum. The encoded frame may be fragmented further according to CoreBluetooth's maximum write length. Notification parsing tolerates fragmentation and coalescing.
- Temporal behavior matters: no subsequent chunk is sent until the matching application acknowledgement arrives; BLE writes are paced. Timeout/disconnection yields an unconfirmed result, not success. No automatic replay follows reconnection.
- Device-info equivalence is limited evidence. This firmware returns a short seven-byte response and does not report every remote state or artwork. Physical display and remote testing are required to validate preservation.

## Verification and operations

`bash scripts/test.sh` exercises wire bytes, arbitrary stream boundaries, independent LZSS decoding, checksum vectors, forbidden commands, payload lengths, pixel layout, rendering, import and saved-design reproducibility. `bash scripts/build.sh` creates an ad-hoc signed app bundle in `dist`. SwiftUI compiler plugins require the normal local Xcode build environment.

Regenerate maps with `.venv/bin/python scripts/generate_cockpit.py`. The code map is a regex inventory, not a semantic Swift call graph. Update the generator's data/output inventory whenever ownership, artifacts or contracts change. Runtime traces, device IDs, local artwork and research source checkouts stay ignored.

Preference verification: the rebuilt app retained both an unchecked choice and then the checked choice through separate quit/relaunch cycles. Restoring the saved image also retained the checked choice. The disconnect-reset handler was removed. Bluetooth was off during the final reconnect attempt, so that path was not exercised on hardware during this preference-only update. No panel content was sent.

## iPhone application

The iOS target reuses `Protocol.swift`, `Bluetooth.swift`, `Design.swift`, `PixelPreview.swift` and `PixelDrawing.swift`. The rasterizer selects AppKit on macOS and UIKit on iOS. The independent iPhone entry point in `PhoneStudio.swift` presents Bikes, Studio and Saved Designs. No third-party dependency or web Bluetooth layer is involved. The existing Mac app remains a separate product.

`LibraryStore` owns a version-2 local JSON document: two named bike profiles, a selected profile, separate drafts and up to 200 reusable designs. SwiftUI bindings update the selected draft; debounced atomic writes and a background flush persist it. Decode/validation failures retain the original file and use safe defaults with saving blocked. The fixed UUID-to-bike assignment is private, phone-local state. A RIGHT notification alone cannot verify ownership: testing observed one remote triggering both physical panels. Setup now requires physical isolation of the intended panel plus explicit confirmation that its large LED display showed the arrow; discovery order, signal strength or a remote indicator LED cannot establish ownership. The same identifier cannot be assigned to both bikes. Discovery displays its existing saved owner. Explicit connection reassignment checks the expected source owner and requires an empty destination; it atomically moves only the UUID, preserving both drafts and the design library. Reconnect uses only previously verified identifiers; callbacks from stale peripherals are ignored.

The input/action path retains distinct spatial scales: finger gestures interpolate into a 36×12 integer grid, zoom/pan enlarge hit targets without increasing output resolution, RGB888 design storage quantizes to RGB444 only at encoding. Phone and Mac share version-1 design JSON. Native Photos import uses bounded image decoding. App UI contains no automatic uploads; its fixed bottom button names the destination.

Readiness has separate stages: advertisement profile, connection/channel discovery, initial info query, physical remote identity check, display-on status, then a fresh preflight query per upload. The display-on bit is evidence from observed firmware responses, not a general guarantee of hardware readiness. Indexed acknowledgements and the final exact settings comparison remain necessary. App backgrounding cancels transfer/disconnects; the screen stays awake while busy. An incomplete two-slot update is reported and never automatically replayed.

Phone display controls are a separate, explicit operation: saved bike UUID and idle connected transport → fresh information query → exact `05 00` or `05 01` → matching acknowledgement → fresh information query. `DisplayPowerChange` validates the baseline and permits only the requested power byte to change at verification. The transport grants opcode 05 only for the exact pending Boolean request. Already-matching state needs no write; timeout, disconnect, backgrounding or conflicting state cancels without replay. UI names the selected bike and distinguishes LED display standby from radio shutdown, handheld-remote power and measured battery consumption. Pairing and firmware commands remain blocked. Acknowledgement and reported state still require physical LED/remote verification.

Directional controls select existing artwork via the bike-specific `1B` command, discovered in static vendor bytecode after explicit download-only authorization. They cannot write that artwork. The fixed `BikeProtocol.Signal` enum exposes modes 0–4, including return to ordinary artwork. Selected-bike identity and idle transport → fresh display-on info baseline → exact scoped `1B <mode>` → paced `1C` mode query → exact mode reply → unchanged-info query. `1E` notifications update observed state but do not substitute for the requested query. A conflicting remote event prevents the success claim. UI places large direction buttons in an expandable Signals section beside display controls. Backgrounding/disconnect clears pending state, with no automatic replay or return-to-artwork command; the physical remote remains available. Physical acceptance is separate from protocol checks: device testing confirmed all four phone signals, return to artwork, selected-panel targeting, and preserved remote operation on the tested panel on 2026-10-20. The reference's distinct UX-family `1C 01` selector is never used for these bikes.

Static research stays outside the application boundary: manufacturer-hosted ZIP byte ranges, CRC/SHA checks, and a locally authored Python standard-library DEX parser in ignored `.research/vendor-static`. Vendor bytecode is treated only as data and never installed, imported, executed or connected to a phone. No runtime dependency was added. Provenance and relevant bytecode excerpts are retained locally; protocol facts and a DEX hash are documented in `docs/protocol.md`.

## Read-only remote diagnostics

`scripts/scan_advertisements.sh` builds a small CoreBluetooth-only CLI with a Bluetooth usage description. Its independent scanner has no connection or GATT read/write code and does not share the content transport. A user-triggered 5–45 second unfiltered discovery records first and final observations plus callback counts to ignored JSONL. This broadens discovery beyond the panel-only FFF0 filter while keeping unknown devices outside the write path. Names can be cached and identifiers can rotate; callbacks are not guaranteed RF packet samples. Button-correlated or on/off observations are evidence for attribution, not proof from signal strength alone. A non-advertising Bluetooth central or proprietary-radio remote can remain invisible. These scans cannot measure power consumption.

## Bundled Halloween collection

`iOS/iLedBikeMobile/HalloweenDesigns.swift` defines six immutable templates: four original 36×12 pixel drawings and two scrolling messages. Native-resolution row patterns preserve intentional single-pixel features; the ordinary encoder and quantized preview remain the rendering boundary. The Designs tab copies the chosen template into the selected bike’s draft only. Existing profiles, saved designs, checkbox preference, command scopes and transport are unchanged. Template selection never sends a BLE command. Users can edit and save their own copy through the existing library workflow. The Mac offline checks validate and encode every preset and generate ignored preview PNGs. No dependencies or persisted schemas changed.

Halloween update verification (2026-10-30): all six templates validated and encoded in the Mac offline checks; the existing 10-test iPhone simulator suite passed. The signed device build installed and launched on the connected iPhone. Pre/post-install library JSON compared equal, preserving both bike profiles and the existing saved design. Artwork previews were visually inspected locally; these new designs have not yet been physically checked on the LED panel. Focused source and script secret scans passed.

## Neutral profile identifiers

New libraries use Bike 1 and Bike 2, with stable identifiers `bike-1` and `bike-2`. Version-1 libraries migrate by their existing profile order, preserving custom names, peripheral assignments, selected profile, drafts and saved artwork. Duplicate or unrecognized profile mappings fail without overwriting the original. Loading alone does not write the migration; a later explicit or debounced save writes version 2.

## Development tooling scope

The supported build and test paths use the shared app sources and the two test suites. The retired standalone upload probe is excluded from the repository and retained only in ignored local research storage. The bounded read-only advertisement scanner remains supported diagnostic tooling; it is separate from content uploads.
